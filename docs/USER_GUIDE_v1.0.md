# Руководство пользователя — Конструктор Саркофагов v2.3.0

## Зачем нужен конструктор

Конструктор собирает переносимый документ о проекте: его назначении, правилах, текущем состоянии, архитектуре, выбранных модулях, рисках и инструкциях для следующего AI. Это не автоматический аудит и не источник истины сам по себе. Точность итогового саркофага зависит от фактов, которые внёс владелец проекта.

## Как проходить мастер

### Этап 0. Выбор типа проекта

- **A — активный продукт:** один развиваемый продукт: игра, сайт, приложение или сервис.
- **B — экосистема:** несколько связанных приложений или сервисов с общими правилами и связями.
- **C — закрытый проект / урок:** проект завершён, заморожен или нужен для фиксации результатов и повторно используемых выводов.
- **D — сложное ядро:** сложная система с архитектурными слоями, безопасностью, интеграциями, тестами и доказательствами.

Выбирай по фактической природе проекта, а не по престижности типа. Тип определяет список рекомендуемых модулей на этапе 2.

### Этап 1. Обязательное ядро

1. **Название:** точное имя проекта.
2. **Версия саркофага:** версия документа передачи контекста. Для первой фиксации обычно `1.0`; это не обязательно версия приложения.
3. **Дата:** дата, на которую проверено описанное состояние.
4. **Статус:** стабильный, в разработке, требует внимания или закрыт. Выбирай честно.
5. **Философия / принципы:** 4–10 правил, которые нельзя нарушать. Пиши отдельными строками и формулируй конкретно.
6. **Назначение:** кому и какую проблему решает проект, какой результат даёт.
7. **Архитектура:** реальные технологии, папки, слои, хранилища и интеграции. Отделяй реализованное от планов. Не вставляй секреты.

### Этап 2. Модули

Конструктор показывает модули, подходящие выбранному типу. Обязательные нельзя отключить; дополнительные включай только при реальной необходимости. У каждого модуля есть большая шпаргалка и поле для фактов.

Правило заполнения: замени общие примеры на текущее состояние проекта. Хорошая запись содержит конкретный компонент, статус, дату/версию и доказательство (тест, файл, коммит, URL или ручная проверка). Если данных нет, так и укажи: «не проверено» или «неизвестно».

### Этап 3. Опциональные блоки

Для каждого блока выбери «Да», если хочешь отдельный раздел в итоговом документе, или «Нет», если сведения уже покрыты выбранными модулями либо пока не нужны.

- **Фактический статус:** что реально работает и чем подтверждено.
- **Чек-листы:** повторяемые процедуры и контрольные действия.
- **Риски:** дефекты, ограничения, неопределённости и их влияние.
- **История изменений:** что изменилось относительно предыдущей версии саркофага.
- **Ссылки:** репозиторий, демо, документация и другие точки доступа. Не включай токены и приватные секреты.

При выборе «Да» заполни появившееся поле. Не дублируй большие разделы без необходимости.

### Этап 4. Финализация

- **Памятка для AI:** стандартная подходит для большинства случаев. Своя нужна, если у проекта есть особый порядок старта, запреты или обязательные проверки.
- **Критически важное:** внеси исключения и предупреждения, которые не удалось разместить выше. Если таких сведений нет — оставь поле пустым.
- Нажми «Сгенерировать», затем прочитай SHORT и FULL. Проверь даты, статусы, названия и формулировки перед передачей другому AI.

## Режим «Диагност»

Опиши проблему, цель, текущее состояние и ограничения. Режим выдаёт предварительную рекомендацию на основе локальных правил/совпадений текста. Это не подключённая языковая модель и не экспертный аудит. Применённые значения обязательно проверь вручную.

## Сохранение и перенос

- Черновик сохраняется локально в браузере на этом устройстве.
- Экспорт JSON — резервная копия структурированных данных, чтобы перенести черновик.
- Импорт JSON — восстановление ранее сохранённого проекта. Перед импортом сохрани текущий черновик.
- SHORT — краткая капсула для быстрого старта новой сессии.
- FULL — подробный документ передачи проекта.

## Как выглядит хорошее заполнение

Плохо: «Безопасность важна, всё проверено».

Хорошо: «RBAC: роли Admin/Accountant/Operator; доступ проверяется middleware; тест `authorization.test.ts` — 12/12 PASS на коммите `<hash>`; production-проверка не выполнялась».

Не выдавай намерения за готовые функции. Не скрывай провалы тестов. Не вставляй пароли, API-ключи, приватные токены и персональные данные.

## Рекомендуемый рабочий ритуал

1. Сохрани JSON-копию текущего черновика.
2. Заполняй этапы по порядку, пользуясь большими шпаргалками под каждым полем.
3. Для неизвестных данных прямо указывай, что они не проверены.
4. Перед генерацией проверь обязательные поля и не оставляй шаблонные примеры как будто это факты проекта.
5. Прочитай FULL целиком и исправь неточности.
6. Сохрани JSON и оба документа в папку проекта с датой контрольной точки.
7. При передаче новому AI приложи саркофаг и сформулируй конкретную следующую задачу. Окончательные решения остаются за владельцем проекта.
